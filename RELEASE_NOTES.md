# opnDossier v1.8.1: the rules the firewall actually loads

v1.8.1 is a bug-fix release that continues the v1.8.0 theme: reading `config.xml` the way the firewall does rather than the way an older release wrote it. Two of the fixes are large. On OPNsense 26.7 the factory default keeps its firewall rules in the MVC filter model and leaves `<filter>` empty, and opnDossier read that model as one opaque string, so a 26.7 firewall converted to zero rules and every rule check passed for lack of input. OPNsense 24.1 moved gateways into a model the same way, so an upgraded firewall exported no gateways. Neither produced a warning, and the exit code was 0.

The rest tightens the shadow analysis, `diff` and the red audit so they stop under-reporting: `diff` compares aliases for the first time, `--normalize` no longer hides real changes, a negated endpoint is read and shown as negated, and pfSense interface rules are evaluated first-match as pfSense does.

## Breaking changes

None in the stability-tracked packages. The `pkg/model`, `pkg/parser`, `pkg/parser/opnsense` and `pkg/parser/pfsense` API snapshots only gained things.

- `model.NamedObject` gains `disabled`, `proto`, `interface`, `pathExpression` and `expire`. ([#964](https://github.com/EvilBit-Labs/opnDossier/pull/964))
- `model.RuleEndpoint` gains `addressRefs`, one reference per alias in a comma-separated address list. Because the new field is a slice, `RuleEndpoint` is no longer a comparable type: code that compares two endpoints with `==` stops compiling and needs a field-wise comparison. `opnDossier`'s own diff engine had exactly that bug (two parses of one config compared unequal whenever a rule named an alias), so this is the compiler catching what the tests did not. ([#911](https://github.com/EvilBit-Labs/opnDossier/pull/911))

`pkg/schema` is public but follows the vendor (see [`docs/development/public-api.md`](./docs/development/public-api.md)), and several of its types change here to match what the firewalls read. If you unmarshal `config.xml` through these types yourself, review the following.

- `opnsense.Rule.Quick`, `Rule.Floating` and `Rule.Disabled`, and `pfsense.FilterRule.Quick`, `FilterRule.Floating` and `FilterRule.Disabled`, are `*string`. pfSense tests all three for presence (`isset()`); OPNsense tests `<floating>` for presence and `<quick>` and `<disabled>` with `!empty()`. Neither uses the liberal boolean vocabulary `BoolFlag` applies, and the difference changed findings (see Fixed). ([#958](https://github.com/EvilBit-Labs/opnDossier/pull/958), [#978](https://github.com/EvilBit-Labs/opnDossier/pull/978))
- `opnsense.OPNsense.Firewall.Filter.Rules` is `[]FirewallFilterRule`, bound to `rules>rule`, instead of a string. ([#911](https://github.com/EvilBit-Labs/opnDossier/pull/911))
- `opnsense.Gateway.MonitorDisable` is a `*string`, and the new `GatewayModelItem` embeds `Gateway` for items under `<OPNsense><Gateways>`. ([#959](https://github.com/EvilBit-Labs/opnDossier/pull/959))
- `opnsense.Alias` binds `<enabled>`, `<description>`, `<proto>`, `<interface>`, `<path_expression>`, `<expire>`, `<url>` and the repeated `<aliasurl>`. ([#964](https://github.com/EvilBit-Labs/opnDossier/pull/964))
- `opnsense.Route.Enabled` (`*string`) and the `<staticroutes>` `version` attribute are bound; `IDS.General.Mode` is bound; `GatewayGroup` binds `<item2>` to `<item5>`. ([#961](https://github.com/EvilBit-Labs/opnDossier/pull/961), [#962](https://github.com/EvilBit-Labs/opnDossier/pull/962), [#963](https://github.com/EvilBit-Labs/opnDossier/pull/963))

Two CLI surfaces change.

- `diff --normalize` normalizes whitespace and addresses only. The port normalizer is gone: it stripped leading zeros from any digits-only value, so a hostname of `007` becoming `7` was reported as no change. ([#940](https://github.com/EvilBit-Labs/opnDossier/pull/940))
- The high-severity "firewall rule has empty type" conversion warning is gone. Both firewalls load such a rule as `pass`, and the converters now do too. ([#960](https://github.com/EvilBit-Labs/opnDossier/pull/960))
- The GitHub Action's default `version:` input is `v1.8.1`. Re-pin your `uses:` lines.

## Fixed

**OPNsense firewall rules kept in the filter model were never read.** OPNsense loads rules from `<filter><rule>` and from `<OPNsense><Firewall><Filter><rules><rule>`. Up to 25.7 the second store was the optional "Automation: Filter" page; in 26.1 it is "Rules [new]"; from 26.7 it is the rules page, and the factory default keeps its two LAN rules there. The schema bound it as one string, so those rules reached no output and nothing warned. The parser now binds the model's rule and converts it into the legacy spelling the checks compare against (`keep` becomes `keep state`, `TCP` becomes `tcp`, service names become port numbers), applies the model's defaults to elements a rule leaves out, derives floating from the interface list, orders both stores in the firewall's evaluation order, and warns on a model version it has not been checked against. Legacy rules take the same defaults so a rule reads alike in both stores; a `diff` between the 26.1 and 26.7 factory defaults no longer reports the two LAN rules as modified with identical text. Fixes [#879](https://github.com/EvilBit-Labs/opnDossier/issues/879). ([#911](https://github.com/EvilBit-Labs/opnDossier/pull/911), [#934](https://github.com/EvilBit-Labs/opnDossier/pull/934))

**OPNsense gateways migrated to the 24.1 model were never read.** OPNsense 24.1 copies each gateway into `<OPNsense><Gateways>` and deletes the legacy `<gateway_item>`. The schema bound only the legacy element, so on an upgraded config `routing.gateways` was empty and `diff` against the pre-upgrade config reported the routing section as removed. The converter reads the model when it holds a gateway and `<gateways>` otherwise, the rule the vendor's own iterator follows, drops the empty placeholder item from both stores, reduces the model's `0`/`1` flags to the legacy presence form so a non-default gateway does not export `"defaultGw": "0"`, fills in the `inet` and weight `1` defaults the firewall applies, keeps the later of two items sharing a uuid with a warning, and warns on legacy gateways a populated model supersedes. ([#959](https://github.com/EvilBit-Labs/opnDossier/pull/959))

**The shadow analysis evaluated pfSense interface rules last-match.** pfSense writes `<quick>` only on floating rules and compiles every other rule as quick. The converter read the element alone, so on the shipped pfSense fixture the block rule leading each of three interfaces was reported as fully shadowed by the rules below it, and `audit` recommended removing it. Interface rules now default to quick. Floating, quick and disabled are read with each vendor's own test: pfSense tests all three for presence, and OPNsense tests `<floating>` for presence and `<quick>` and `<disabled>` with `!empty()`, so an empty `<floating/>` is floating on both. Direction follows pfSense's `floating=yes` check, floating rules bound to an interface are ordered ahead of its interface rules, and a disabled rule can no longer win a pair or stop a default deny from being terminal. Fixes [#921](https://github.com/EvilBit-Labs/opnDossier/issues/921). ([#958](https://github.com/EvilBit-Labs/opnDossier/pull/958))

**An unticked Quick box on an OPNsense legacy rule read as quick.** The legacy rules page stores it as `<quick>0</quick>`; the converter forced "quick unless floating" onto every non-floating rule and the shadow analysis reported the block below it as a bypassed deny, where the firewall evaluates the rule last-match and the block wins. An empty `<floating/>` read as not floating; the firewall tests it with `isset()`. Fixes [#976](https://github.com/EvilBit-Labs/opnDossier/issues/976). ([#978](https://github.com/EvilBit-Labs/opnDossier/pull/978), [#985](https://github.com/EvilBit-Labs/opnDossier/pull/985))

**A filter rule with no `<type>` was skipped by every pass-rule check.** Both firewalls load it as pass, and pfSense writes the companion rule of every port forward without one. On the shipped pfSense fixture the red audit reported neither port forward and `FIREWALL-023` passed. Both converters now read an empty type as pass, and pfSense also takes `keep state` where `<statetype>` is absent, so a TCP forward's rule no longer fails `SANS-FW-007` as stateless. Reading those rules exposed a red-audit false positive: a WAN pass rule whose destination is a port forward's target was counted as exposing the firewall's own web GUI, although pf matches it after rdr against the internal host. Such a rule is now skipped unless the target is or spans an address of the firewall itself, walking aliases and network groups to decide. The empty `<rule/>` OPNsense leaves under `<filter>` after the last legacy rule is deleted is dropped as a placeholder instead of read as an any-to-any pass rule. ([#960](https://github.com/EvilBit-Labs/opnDossier/pull/960))

**`diff` did not compare aliases.** Widening the port alias of a WAN pass rule to `1:65535` printed "No changes detected", and so did adding or removing an alias. A new `aliases` section pairs aliases by name and reports one entry per changed field, rated medium when an enabled firewall rule, outbound NAT rule or port forward uses the alias, directly or through a group, and low otherwise. To make that comparison honest the schema now reads `<enabled>` (a disabled OPNsense alias loads with no members), the model's `<description>`, and the legacy `<url>` and `<aliasurl>` sources, and both outbound NAT converters resolve an alias written to `<network>`, where both GUIs put it, so such an alias no longer appears as unused. ([#964](https://github.com/EvilBit-Labs/opnDossier/pull/964))

**`diff --normalize` dropped real changes.** The engine skipped a modified entry whenever its two displayed values normalized equal, without asking whether the displayed text was what had been compared. A firewall rule, an outbound NAT rule and a port forward display as a one-line summary of a few fields, and a modified user displays nothing, so a rule gaining logging, a forward sent to another port and a replaced API key each printed "No changes detected". Those entries are marked as summarized and are never skipped. Separately, the port normalizer equated `007` and `7` in any digits-only field, and the address normalizer read `172.016.000.001` as `172.16.0.1`, which it is not on FreeBSD (`inet_aton` reads a zero-led octet as octal). Both are gone; a zero-padded address is reported as written. Fixes [#882](https://github.com/EvilBit-Labs/opnDossier/issues/882), [#918](https://github.com/EvilBit-Labs/opnDossier/issues/918). ([#914](https://github.com/EvilBit-Labs/opnDossier/pull/914), [#940](https://github.com/EvilBit-Labs/opnDossier/pull/940), [#936](https://github.com/EvilBit-Labs/opnDossier/pull/936))

**Negated endpoints were dropped, hidden or misread.** Both outbound NAT converters lost the `<not>` flag, so a rule translating everything except the LAN net exported as a rule translating the LAN net. The firewall rules and outbound NAT tables printed a negated address bare; they now prefix it with `!` as the OPNsense rule list does. And `analysis.IsAnyEndpoint` read a negated `any` as matching nothing, so a pass rule from an inverted `any` passed `FIREWALL-022`, `FIREWALL-023` and the SANS and STIG equivalents; neither firewall inverts `any`, and it is now counted as every host. A negated `0.0.0.0/0` still matches nothing, as both firewalls compile it. Fixes [#920](https://github.com/EvilBit-Labs/opnDossier/issues/920), [#929](https://github.com/EvilBit-Labs/opnDossier/issues/929), [#930](https://github.com/EvilBit-Labs/opnDossier/issues/930). ([#928](https://github.com/EvilBit-Labs/opnDossier/pull/928), [#931](https://github.com/EvilBit-Labs/opnDossier/pull/931), [#939](https://github.com/EvilBit-Labs/opnDossier/pull/939))

**Three more OPNsense migrations deleted the element opnDossier read.** OPNsense 26.1 replaced the IDS `<ips>` checkbox with a `<mode>` option, so Suricata running inline read as detection only and the security score was 10 points low; `IsIPSMode` follows the model version and reads `netmap` and `divert` as IPS, with `divert` counted only when a filter rule actually diverts to it. ([#962](https://github.com/EvilBit-Labs/opnDossier/pull/962)) OPNsense 26.7 stores gateway group tiers 2 to 5 in `<item2>` to `<item5>`, so every gateway below tier 1 was missing from the export; all five tiers are read in tier order. ([#963](https://github.com/EvilBit-Labs/opnDossier/pull/963)) OPNsense 26.1.10 replaced each static route's `<disabled>` with `<enabled>`, so every disabled route read as enabled; a present `<enabled>` wins and older configs read as before. ([#961](https://github.com/EvilBit-Labs/opnDossier/pull/961))

**Smaller fixes.** Port forwards with a signed or space-padded `<sequence>` are ordered by the firewall's natural-sort key rather than the parsed integer. ([#935](https://github.com/EvilBit-Labs/opnDossier/pull/935)) `validate` accepts `inet46` and `modulate state` on OPNsense legacy rules, both of which the rule editor offers. ([#941](https://github.com/EvilBit-Labs/opnDossier/pull/941)) `diff --security` keeps an interface being enabled or disabled; the rating pattern matched `.enable` and the analyzer emits `.enabled`. ([#924](https://github.com/EvilBit-Labs/opnDossier/pull/924))

## Upgrade notes

Upgrading is a drop-in replacement. No config changes, no CLI flag changes. But this release reads configuration it used to discard, so expect your output to change.

**OPNsense 26.7 users see firewall rules for the first time.** Every report, export, audit and diff of a config whose rules live in the filter model now includes them. Checks that passed on an empty rule set will now evaluate real rules. These are not new checks. Read the new findings before you call it a regression.

**Shadow-analysis findings move on both vendors.** pfSense interface rules are first-match now, so a block rule above permissive rules is no longer reported as shadowed, and a pass above a block is reported as bypassing it, with the block as the shadowed rule. OPNsense rules with `<quick>0</quick>` go the other way. Disabled rules no longer produce `high` or `critical` findings as winners.

**Audits may now fail `FIREWALL-022`, `FIREWALL-023` and the SANS equivalents** on a rule with an inverted `any` endpoint, and the red audit may stop reporting a WAN-exposed web GUI that was really a port forward's companion rule.

**Exports gain fields.** `routing.gateways` on upgraded OPNsense configs, `negated` on outbound NAT endpoints, `addressRefs` on rule endpoints, `disabled`, `proto`, `interface`, `pathExpression` and `expire` on aliases, and gateway group tiers 2 to 5. Golden files and snapshot tests will need regenerating.

**`diff` output changes.** A new `aliases` section; `--normalize` reports changes it used to hide; `--security` includes interface enable changes.

**GitHub Action users should re-pin to `v1.8.1`.**
